# Мультипроектный Канбан для Bitrix24

Локальное/встраиваемое приложение: **одна сводная канбан-доска** по задачам из нескольких проектов и задачам без проекта («только для себя»).

Источник правды — Bitrix24. Приложение **не копирует** задачи на вторую доску: это view + маппинг стадий. Drag-and-drop вызывает `task.stages.movetask` в родном проекте задачи.

## Возможности MVP

- Выбор нескольких проектов (`GROUP_ID`)
- Опция «задачи без проекта» (личные / «Мой план»)
- Единые логические колонки: К выполнению / В работе / На проверке / Готово
- Настраиваемый маппинг стадий проектов → логические колонки
- Drag-and-drop → смена стадии в исходном проекте
- Клик по карточке → открытие задачи в Bitrix (`BX24.openPath` или ссылка)
- Фильтры: исполнитель, проект, поиск по названию
- Пустые / loading / error состояния + блок диагностики
- **Mock-режим** для разработки без портала

## Стек

- TypeScript + Next.js 15 (App Router)
- React 19
- `@dnd-kit` для drag-and-drop
- Bitrix24 REST (входящий вебхук на старте, задел под OAuth)

## Модель личных задач (без проекта)

Выбрана явная модель:

1. Личные задачи загружаются отдельно (фильтр `GROUP_ID = 0` / без группы).
2. Стадии берутся из канбана **«Мой план»** (`task.stages.get` с `entityId: 0`).
3. На сводной доске они попадают в те же логические колонки через маппинг ключей `0:<STAGE_ID>`.
4. Это не клон карточки и не отдельная «правдивая» доска — только отображение + перенос стадии.

## Подключение входящего вебхука

1. В Bitrix24: **Разработчикам → Другое → Входящий вебхук**.
2. Права (scopes) минимум:
   - `task` — задачи и стадии
   - `sonet_group` / группы — список проектов
   - `user` / `user_brief` — фильтр исполнителей
3. Скопируйте URL вида  
   `https://<портал>.bitrix24.ru/rest/<user_id>/<token>/`
4. В `.env.local`:

```env
BITRIX_MODE=webhook
BITRIX_WEBHOOK_URL=https://your-portal.bitrix24.ru/rest/1/xxxxxxxx/
BITRIX_PORTAL_URL=https://your-portal.bitrix24.ru
```

5. Перезапустите `npm run dev`.

Вебхук вызывается **только на сервере** (API routes), токен не уходит в браузер.

## Локальное приложение (OAuth) — задел

Для нескольких пользователей и встраивания в меню Bitrix:

1. Создайте локальное приложение в портале.
2. Укажите путь обработчика (URL вашего деплоя) и права: `task`, группы, пользователи.
3. Заполните в `.env.local`:

```env
BITRIX_MODE=oauth
BITRIX_OAUTH_CLIENT_ID=...
BITRIX_OAUTH_CLIENT_SECRET=...
BITRIX_OAUTH_REDIRECT_URI=http://localhost:3000/api/oauth/callback
```

Сейчас OAuth-обмен токенами **не реализован end-to-end** (задел в конфиге и клиенте). Для MVP используйте webhook или mock. Встраивание: подключите `BX24` JS API — клик по карточке уже пробует `BX24.openPath`.

## Маппинг стадий

Кнопка **«Маппинг стадий»** открывает таблицу:

| Проект / Мой план | Стадия Bitrix | Колонка сводной доски |
|-------------------|---------------|------------------------|
| Проект Альфа      | Новые         | К выполнению           |
| Проект Бета       | Backlog       | К выполнению           |
| …                 | …             | …                      |

Ключ маппинга: `<entityId>:<stageId>` (для личных `entityId = 0`).

Маппинг хранится в `localStorage` браузера. Без маппинга задачи **не попадают в колонки** (как часто бывает с Маркет-приложением на проде) — они видны в блоке «Задачи без маппинга».

## Архитектура

```
Bitrix24 (источник правды)
  → REST (tasks / stages / groups / users)
  → Next.js API: агрегация + маппинг стадий → колонки
  → UI сводного канбана
  → drag → task.stages.movetask в STAGE_ID того GROUP_ID, где живёт задача
```

### Ключевые REST-методы

| Метод | Назначение |
|-------|------------|
| `tasks.task.list` | Задачи (фильтр `GROUP_ID`, `RESPONSIBLE_ID`, …) |
| `task.stages.get` | Стадии канбана (`entityId` = ID группы, `0` = Мой план) |
| `task.stages.movetask` | Перенос задачи между стадиями |
| `task.stages.canmovetask` | Проверка прав |
| `sonet_group.get` | Список проектов |
| `user.get` | Исполнители для фильтра |

## Диагностика «пустой» доски

Типичные причины (в т.ч. почему Маркет мог молчать в проде):

1. **Права / scopes** вебхука или приложения
2. **Другие ID проектов** на рабочем портале
3. **Задачи без `GROUP_ID`** не включены в выборку
4. **Вебхук/OAuth смотрит на другой портал**
5. **Стадии не замаплены** на логические колонки

В UI разверните блок **«Диагностика»**: какие `groupId` запрошены, сколько задач вернулось, ошибки access.
